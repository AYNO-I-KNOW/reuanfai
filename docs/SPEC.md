# SPEC — เรือนไฟ

> เพื่อนคู่ใจของแม่หลังคลอด บอกได้ว่าอยู่ไฟแบบไหนได้ เมื่อไร และจองได้ที่ไหน ตั้งแต่วันคลอดจนครบ 3 เดือน
> ที่มา: `concept/ConceptPaper_v2.pdf`, `concept/UX-Brief_v1.pdf` (ล็อก — ADR-0000)

## 1. เป้าหมาย
คู่มือการจัดบริการผดุงครรภ์ไทยฯ 2569 หน้า 100 ระบุว่าควรมี 4 ระบบ เรือนไฟทำ 3 ระบบให้ทำงานต่อกันในระบบเดียว:
1. ระบบคัดกรองอาการออนไลน์ → คัดกรอง 3 ชั้น + เช็กอินซ้ำ
2. ระบบแจ้งเตือนและนัดหมายผ่าน LINE OA → จองคิวตามตารางหน่วยบริการ + เตือนทานยา
3. ระบบบริหารจัดการคลังยา → สต็อก, Lot, วันหมดอายุ, ตัดสต็อกตามใบสั่งยา
4. ~~คลังความรู้ดิจิทัล (E-Manual)~~ → ยังไม่ทำ (แสดงแค่ที่มาของเกณฑ์)

## 3. หลักการ (ไม่ต่อรอง)
1. คัดกรองก่อนจอง — จองได้เฉพาะหัตถการที่ผ่านเกณฑ์ อยู่ในกรอบเวลา และยังมีสิทธิ์ เหลือ
2. คนเป็นผู้ตัดสิน ระบบทำหน้าที่ชี้ตามคู่มือ (ADR-0001)
3. ไม่แน่ใจ = ให้คนประเมิน (ADR-0005)
4. ทุกคำตอบบอกที่มาได้ (เลขหน้า + เวอร์ชันกฎ) (ADR-0002) — ใน API/P4/audit · จอแม่ไม่ต้องแสดงเหตุผล (ADR-0014)
5. ข้อมูลไม่ถูกส่งไปไหนถ้าเจ้าของไม่อนุญาต (ADR-0007)

## 5. Workflow
```
UX brief (ล็อก) → ทีม design ส่ง design → DESIGN-REVIEW.md เทียบกับ spec
  → ถ้าขัดกัน: ปรับ design หรือเปิด ADR ใหม่ (เจ้าของตัดสิน)
  → ถ้าผ่าน: implement ตาม phase
```
spec ปรับตาม design ที่เจ้าของอนุมัติแล้วโดย ADR-0014 (route, M3, M4, M6, journal ฯลฯ) ADR-0015 (แชทผู้ช่วย, หน้าชำระเงินสาธิต, ติดต่อด่วนเป็น route) และ ADR-0016 (ติดต่อด่วนในหัวหน้าแรก/แชท, หน้าแก้โปรไฟล์, ชิปอาการใน journal, quick prompt ตามช่วงหลังคลอด) แต่ design ที่อนุมัติแล้วยังต้องผ่าน review ต่อ phase
**ห้ามเริ่ม implement หน้าจอก่อน phase นั้นผ่าน design review** แต่ backend ที่ไม่ขึ้นกับ design (rules engine, schema, booking, stock) เริ่มตาม spec ได้เลย

## 8. ตัวชี้วัด (Concept v2 §5.3)
- ช่วงทดสอบ: ผู้ใช้คัดกรองและจองคิวจนจบเองได้, ผู้ที่เข้าเกณฑ์ส่งต่อเลือกติดต่อโรงพยาบาลได้ถูก, ผู้ใช้เข้าใจว่าผลคัดกรองไม่ได้แปลว่าปลอดภัย
- ช่วงใช้งานจริง: สัดส่วนคนที่มาแล้วรับบริการไม่ได้ (ควรลดลง), ความปวดก่อน–หลัง, การไม่มาตามนัด, ยาขาดสต็อก, ความพึงพอใจ

**เงื่อนไขหยุดแล้วแก้ก่อน:** ส่งต่อช้าลง หรือผู้ใช้ตอบอาการเบากว่าความจริงเพื่อให้จองได้
