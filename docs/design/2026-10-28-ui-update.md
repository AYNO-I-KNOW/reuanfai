# ReuanFai — บันทึกปรับ UI วันที่ 28 ตุลาคม 2569

บันทึกสำหรับทีมพัฒนา ครอบคลุมการแก้ในแชตรอบนี้ตั้งแต่ focus ช่องแชตจนถึง onboarding, avatar และระยะฟอร์ม สรุปพฤติกรรมสุดท้ายที่ตกลงแล้ว ส่วนข้อมูลใน handoff รอบเก่าให้ถือเป็นสถานะ ณ วันที่ของเอกสารนั้น

## 2. ชื่อเล่นและการบันทึกข้อมูล

- ชื่อเล่นบังคับกรอก ยาวไม่เกิน 40 ตัวอักษร ฟอร์มข้อมูลคุณแม่ไม่ผ่านหากว่างหรือมีแต่ whitespace
- ใช้ label แบบนามกระชับให้สอดคล้องกับ “วันคลอด” และ “เบอร์ติดต่อคุณแม่” แทนประโยคสนทนาเดิม
- แยกข้อมูล UI ออกจาก motherProfile เดิม โดยใช้ browser demo store key `ruenfai-mother-identity-v1` รูปแบบ `{nickname: string, avatarId: string}`
- onboarding บันทึกชื่อเล่นขณะพิมพ์และรูปขณะเลือก/สุ่ม จึงจำค่าแม้ยังไม่กดถัดไป
- ฟอร์มแก้ไขโปรไฟล์ใช้ draft ของชื่อเล่น บันทึกเมื่อกดบันทึก และไม่รับชื่อว่าง/whitespace-only; ยกเลิกไม่เปลี่ยนชื่อเล่น
- รูปในหน้าดูโปรไฟล์เปลี่ยนและบันทึกทันทีผ่าน picker; ในหน้าแก้ไขเก็บเป็น draft และบันทึกพร้อมข้อมูลเมื่อกดบันทึก (อัปเดตในหัวข้อ9)
- รหัสรูปเก่าชั่วคราว ruenfai/smile/happy ยังอ่านได้เพื่อรักษาชื่อเล่น; เมื่อ picker mount จะสุ่มเปลี่ยนเป็นรหัสในชุดใหม่หนึ่งครั้ง
- ยังไม่มีการบันทึกชื่อเล่นหรือ avatar ไปบัญชี/เซิร์ฟเวอร์ และไม่ได้เปลี่ยน endpoint หรือสัญญาข้อมูล motherProfile

## 3. แหล่งรูปและพฤติกรรมสุดท้าย

ไฟล์รูปที่ใช้จริงอยู่ `apps/web/public/images/ruenfai/avatars/mother-01.png` ถึง `mother-12.png` เป็นภาพแยกจาก contact sheet ที่สร้างในแชตและผู้ใช้เลือกทั้งชุด ไม่ใช่ asset ดาวน์โหลดจาก Duolingo เลขใต้รูปใน contact sheet ไม่รวมในรูปที่ใช้ในแอป

- รายการรูปอยู่ใน motherAvatars; avatarSource เป็นตัวแปลง id เป็น source ที่ Home/โปรไฟล์ใช้ร่วมกัน
- ผู้ใช้เลือกชุดหน้าตรงรุ่นแรก 01–12; ชุดทดลองบุคลิกอื่นและชุด 13–24 ไม่ได้ใส่ในแอป
- รูปผู้ช่วยในแชต/mascot เดิมยังเป็นคนละบทบาทกับ avatar คุณแม่
- เคยทดลอง crossfade 200ms แล้วผู้ใช้ปฏิเสธหลังลองจริง จึงถอดออกทั้งหมด สถานะสุดท้ายต้องไม่มี opacity animation บนตัวรูป
- ปุ่มสุ่ม: pressed background ลาเวนเดอร์ และ scale .96 พร้อม transition 120ms; reduced motion ไม่ย่อปุ่ม
- การสุ่ม/เลือกมี live region แจ้งเลขรูปให้ screen reader

## 5. Focus และ motion ของชีต

- แชตติดตาม Tab และ pointerdown แยกกัน เพราะ input อาจ match :focus-visible แม้เปิดด้วย pointer
- เปลี่ยนกรอบ focus ของ composer ให้ขึ้นเฉพาะ input ที่ focus หลังใช้ Tab; ปุ่มอื่นยังคง keyboard focus indicator
- PickerSheet เดิมใช้ overflow:hidden บน viewport dialog ซึ่งยังถูกโปรแกรมเลื่อนได้ Native autofocus เลื่อนตัวครอบระหว่าง transform จนชีตดูค้าง
- เปลี่ยนเป็น overflow:clip เฉพาะตัวครอบ ส่วน body ข้างในยัง overflow-y:auto
- คง entry320ms / exit240ms และ reduced-motion ตาม component เดิม การแก้นี้ส่งผลต่อ picker รูป วันที่ และตัวเลือกของฝั่งคุณแม่ที่ใช้ PickerSheet

## 6. หลักฐานการตรวจและข้อจำกัด

ตรวจใน local browser:

- เปิด avatar sheet และเห็นครบ12รูปแบบ4×3; พบ selected state หลังเลือกรูป
- ชื่อเล่นและ avatar จำค่าหลัง reload ระหว่างทดสอบ persistence (ตอนนั้นใช้ catalog ชั่วคราว)
- กดสุ่มแล้วรหัสรูปเปลี่ยน เช่น02→07; เวอร์ชันสุดท้ายตรวจตัวรูปมี1 image และไม่มี active animation
- จับเฟรม PickerSheet ก่อนแก้: sheet topคง598px ขณะที่ dialog scrollTop226→7.5; หลังแก้ sheet topเลื่อน824→598px ต่อเนื่อง โดย scrollTop0 ตลอด และตรวจการเคลื่อนลงตอนปิด
- วัด onboarding: ช่องชื่อเล่น/วันที่/โทรศัพท์/วิธีคลอด/สิทธิ/หน่วยบริการสูง52px, padding13px16px, radius16px; ทุกกลุ่มห่าง24px, label/legend gap8px
- crossfade ที่เคยตรวจมีเฟรม opacity เพิ่มต่อเนื่องและตำแหน่งคงที่ แต่ไม่ถือเป็นพฤติกรรมสุดท้าย เพราะผู้ใช้เลือกให้ถอดออก

ตรวจโค้ด: web typecheck และ ESLint เฉพาะ TS/TSX ที่แก้ผ่าน; git diff --check ผ่าน ตรวจซ้ำครั้งล่าสุดในรอบจัดทำเอกสารนี้; production build ผ่านครบ28 routes ก่อน commit

ยังไม่ได้ตรวจครบ: ทุก route/ทุก responsive breakpoint ของ Clinic/Department หลังเปลี่ยน shared geometry, reduced-motion บนอุปกรณ์จริง, native keyboard/touch บนโทรศัพท์, deploy และ backend integration งาน QA ฝั่ง desktop forms ยังต้องไล่ modal/filter/search และการ wrap หลังปรับ geometry ก่อนนับว่าผ่านทั้งระบบ

## 8. Audit กล่องชวนแชตบน Home — 28 ตุลาคม 2569

สถานะ: ตรวจพฤติกรรมเดิม ยังไม่ได้ปรับ motion ของ ChatInvitation ในรอบ audit นี้ ไม่ควรสรุปว่าผ่านมาตรฐาน accessibility ทั้งระบบ

ไฟล์: `apps/web/src/app/ruenfai/ChatInvitation.tsx`, `bottom-nav.module.css`, `chat-topics.ts`; BottomNav เป็นผู้แสดง component

### พฤติกรรมที่พบ

- รอ2.4วินาทีหลัง mount แล้วแสดงคำถาม; entry280ms ด้วย translateY8px และ opacity
- หลัง400ms เริ่มพิมพ์ทีละ Thai grapheme ทุก65ms จากนั้นค้าง6วินาที
- exit ใช้ opacity240ms และ translateX10px/scale.94 ด้วย transform320ms แต่ phase hidden ถูกตั้งที่240ms จึงซ่อนก่อน transform จบ80ms
- เว้นช่วง แล้ววนหัวข้อถัดไปโดยไม่มีจุดสิ้นสุด ไม่มีปุ่ม pause/stop/hide และไม่หยุด timer เมื่อ hover หรือ keyboard focus
- ขนาดกล่อง width:auto/min-width152px ทำให้เปลี่ยนความกว้างตามข้อความ; จับใน browser ได้152→155→170px ขณะคำถามแรกพิมพ์ครบ และรอบถัดไปกลับ152px
- reduced-motion ปิด CSS motion/การพิมพ์ทีละตัว แต่ยังวนเปลี่ยนหัวข้อและซ่อน/แสดงอัตโนมัติ
- phase hidden ใช้ inert แต่ phase exit ปิดเพียง pointer-events จึงยังมีช่วงที่ keyboard focus ได้ขณะกำลังจางหาย
- ข้อความเป็นคำถามแนะนำ ไม่ใช่ข้อความใหม่จากระบบจริง; การเลียนแบบ typing ต่อเนื่องอาจทำให้เข้าใจสถานะผิดได้ (ข้อประเมิน UX)

### ข้อสรุปและทิศทางเสนอ

ไม่ใช่ปัญหาแค่ duration สั้น/ยาว: ควรแก้การเรียกร้องความสนใจซ้ำ การเปลี่ยนขนาด และการควบคุมข้อความอัตโนมัติก่อน

เสนอให้แสดงคำถามเต็มในพื้นที่ขนาดคงที่ ใช้ entrance สั้นเพียงครั้งเดียวโดยไม่มี typing/scale loop; ให้คำถามอยู่นิ่งจนเลือกหรือปิด และมีวิธีซ่อน คงปุ่มแชตหลักอยู่เสมอ กรณียังต้องหมุนหัวข้อควรมีวิธีหยุดและไม่เปลี่ยนขณะผู้ใช้กำลัง focus/ใช้งาน ส่วน reduced motion ให้แสดงนิ่ง

ค่าระยะเวลาเป็น design choice ที่ต้องลองในบริบทจริง ไม่มีเลข ms เดียวที่รับรองว่า “ผ่านมาตรฐาน”

แหล่งอ้างอิง:
- W3C WCAG2.2 Understanding2.2.2: https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html — ข้อมูลอัปเดตอัตโนมัติที่แสดงควบคู่เนื้อหาอื่นต้องมีวิธี pause/stop/hide หรือควบคุมความถี่ เว้นแต่จำเป็น; เงื่อนไข5วินาทีใช้กับ moving/blinking/scrolling ไม่ใช่ข้อยกเว้นของ auto-updating
- Material motion duration/easing: https://m1.material.io/motion/duration-easing.html — ใช้อ้างหลัก smooth acceleration/deceleration ไม่ใช่การอ้างว่าต้องใช้ easing เดียวกับ Material หรือเป็นข้อรับรอง WCAG

การตรวจครั้งนี้เป็น code review + browser geometry/timing sampling บน local Home ไม่ใช่ full accessibility audit หรือผลบนเครื่องมือถือจริง
