# ADR-0014: ปรับ spec ให้ตรงกับ design ที่อนุมัติแล้ว

- สถานะ: Accepted · 2026-10-06 · ตัดสินโดย Pantawat (dev) ภายใต้อิสระที่เจ้าของโปรเจกต์ (เกรพ) มอบให้ทีม design/dev · ที่มา: `docs/design/handoff.md` §2, §4–§7 (R-01…R-13) · แก้เพิ่ม ADR-0002, ADR-0003, ADR-0005, ADR-0009, ADR-0012 เฉพาะส่วนที่ระบุในตาราง "ส่วนที่เปลี่ยน" · แก้เพิ่มบางส่วนโดย ADR-0015 (ข้อ 6 ตำแหน่งปุ่มติดต่อด่วน)

## บริบท
spec ใน `docs/specs/` เขียนก่อนมี design ทีม design ส่ง prototype + handoff รอบ 1 (2026-10-05) ซึ่งต่างจาก spec/UX brief หลายจุด (R-01…R-13) เจ้าของโปรเจกต์ (เกรพ) ให้อิสระทีม design/dev ตัดสินรายละเอียด dev (Pantawat) จึงรับ design ที่ส่งมอบและปรับ spec ตาม design ตามกลไก ADR-0000 จึงออก ADR นี้ supersede เฉพาะส่วนที่ขัดกัน ส่วนที่ไม่ได้ระบุไว้ที่นี่ไม่เปลี่ยน

## ตัดสินใจ
รับ R-01…R-13 และข้อ ❌ ใน handoff §6 เป็น spec ใหม่ทั้งหมด:
1. **Route (R-01, R-06)**: แม่ `ruenfai/*` · หน่วยบริการ `clinic` (หน้าเดียว สลับ view ด้วย state) · กรมฯ `department` (หน้าเดียว สลับ view) · `growth` `baby` `profile` เป็น alias ของ prototype ไม่ใช่ feature · `/dtam`, `/dtam/design-system` นอกขอบเขต
2. **M3 (R-02)**: ฟอร์มต่อช่วง 7/6/7 แสดง **ทุกข้อให้ทุกคน** ไม่ซ่อนตาม `askIf` ใน UI ไม่ไปข้อถัดไปอัตโนมัติ ไม่มีปุ่ม "โทรปรึกษา" ตอน unsure · rules engine ยัง pure/deterministic และ **ตัดคำตอบของข้อที่ `askIf` เป็น false สำหรับแม่คนนั้นทิ้ง**ก่อนคำนวณ
3. **M4 (R-03)**: แสดง 3 สถานะตาม design ไม่ต้องแตะดูเหตุผล/เลขหน้าบนจอแม่ ไม่ต้องมีข้อความ "ไม่ใช่ผลการวินิจฉัย" · engine/API ยังคืน `reasons` + `ref` และ `ProcStatus` ยัง 4 ค่า · วิธีแสดง `not_yet` ใน 3 สถานะ = คำถามเปิด (SPEC Q9)
4. **M6 (R-04)**: หน้าเดียว (หน่วย/หัตถการ/สิทธิ์/วัน/เวลา) + confirmation + success · กฎฝั่ง server (window ∩ quota ∩ same-day, referral lock, error codes) ไม่เปลี่ยน
5. **Journal (R-05)**: เพิ่มเข้า scope — บันทึกอารมณ์ 5 ระดับ + ข้อความ (หน้า M13, `/me/journal`, ตาราง `journal_entries`) เป็นข้อมูลสุขภาพ **ห้ามอยู่ในข้อความ LINE** (ADR-0006) · consent/การแชร์ = SPEC Q11 (ระหว่างนี้เห็นเฉพาะเจ้าของ ไม่เข้า share / `agg_*` / AI)
6. **เบอร์ติดต่อ (R-07)**: แม่มี `phone`, `emergencyPhone` (บังคับใน M2) · ติดต่อด่วนเป็นปุ่มใน bottom nav เปิด sheet (ไม่ใช่มุมขวาบน) ไม่ต้องมีทุกหน้า ไม่ต้องมีรายการ 7 อาการส่งต่อ
7. **เจ้าหน้าที่สร้างนัด (R-08)**: `staff` สร้างนัดด้วยชื่อ (free text) + เบอร์ ผ่าน `POST /provider/appointments` · ผูกกับ record แม่อย่างไร = SPEC Q12
8. **ยา (R-09)**: `pharmacist` สร้าง/แก้ไขยาและรูปได้ · stock ฝั่ง backend ยังเป็น lot-based FEFO (UI แสดงยอดรวมต่อยาได้)
9. **รีวิว (R-10)**: ฝั่งหน่วยบริการกรอง/ดูรีวิวรายแพทย์ได้ · ติดตามอาการไม่พึงประสงค์ = ผู้รับผิดชอบ + สถานะ 3 ค่า + บันทึก (ขยาย `staff_alerts`) · ฟอร์มรีวิวฝั่งแม่ไม่มี `painAfter`/adverse → เป็น optional · ต้นทางของ pain หลังรับบริการ/adverse ฝั่งกรมฯ = SPEC Q10
10. **จัดการแพทย์ (R-11)**: เพิ่มแพทย์ + รูป + สีการ์ด (`staff.photo_url`, `staff.color`) · duration/capacity/start-days/template ของ P2 ยังอยู่ใน spec (design ต้องเพิ่ม)
11. **กรมฯ (R-12)**: layout/ตัวกรอง/การจัดกลุ่มตาม design (D4 อยู่ใน view ของ D1, D6 อยู่ใน view ของ D2) · ข้อมูลจริงยังมาจาก `agg_*` + suppression n<5 เท่านั้น
12. **ข้อความ/ป้าย (R-13, §6)**: คำถามรายข้อ 14px ได้ · ตัวเลือกที่เลือกใช้พื้น lavender (ไม่ใช้ขอบหนา) · ฝั่งหน่วยบริการไม่ต้องมีป้าย "ข้อมูลจำลอง" · ชื่อหน่วย/แพทย์ไม่ต้องมี "(ตัวอย่าง)" · P8 ไม่ต้องมีป้าย "สรุปโดย AI"
13. หน้าที่ design ยังไม่ส่ง (M0, M4-R, M8, M11, D8) **คงอยู่ใน spec** ทีม design ยังค้างส่ง

## ไม่เปลี่ยน
- ADR-0001: engine pure ไม่มี LLM/I/O · AI ห้ามเห็นข้อความ "ไม่แน่ใจ"
- ADR-0005 แกนหลัก: `unsure` **ห้ามถือเป็นผ่าน** (ข้อที่ applies แล้วตอบ unsure → ตาม `onUnsure` เหมือนเดิม) · `referral_lock` · ปุ่ม มี/ไม่มี/ไม่แน่ใจ ขนาดเท่ากัน · ห้ามคำว่า "ปลอดภัย" · ข้อความ unsure ส่งถึง P4
- ADR-0006: ไม่มีข้อมูลสุขภาพ (รวม journal, ผลคัดกรอง, ชื่อยา) ในข้อความ LINE
- ADR-0007: consent 2 ชั้น · ติ๊กแชร์เองทุกครั้งที่จอง (design ต้องเพิ่มช่องนี้)
- ADR-0008: กรมฯ ใช้ `agg_*` + n<5 เท่านั้น · ชุดตัวกรองมาตรฐาน (เขต, จังหวัด, หน่วย, ช่วงเวลา, วิธีคลอด)
- ADR-0012: ข้อมูลจำลองเท่านั้น ไม่มีข้อมูลบุคคลจริง · ไม่เชื่อมระบบจริง · ติ๊ก "ตรวจสอบสิทธิ" ก่อนบันทึก
- ADR-0004, 0010, 0011, 0013 · เกณฑ์ ruleset ทั้งหมด (rules §3–§7)

## ผลที่ตามมา
- spec ที่แก้ตาม ADR นี้อ้าง "ADR-0014" ในจุดที่เปลี่ยน · คำถามที่ design ไม่ตอบ เพิ่มเป็น SPEC Q9–Q20 ไม่เดาเอง
- design ที่อนุมัติแล้วไม่เท่ากับผ่าน `DESIGN-REVIEW.md` · กฎ CLAUDE.md ข้อ 2 ยังใช้ต่อ phase
- engine ต้องมี `applies` ต่อข้อ และตัดคำตอบข้อที่ไม่ applies · `POST /me/screenings` ต้องปฏิเสธถ้าข้อที่ applies ไม่มีคำตอบ (ห้ามถือว่าไม่ตอบ = ผ่าน)
- ฟอร์ม M3 ทั้ง 3 ช่วงอาจทำให้แม่ที่เข้าเกณฑ์ส่งต่อไปถึง M4-R ช้ากว่าเดิม → จังหวะส่งคำตอบต้องตัดสิน (Q15)
- department ใน prototype อ่าน `careDemo` รายคน — production ห้าม (ADR-0008)
